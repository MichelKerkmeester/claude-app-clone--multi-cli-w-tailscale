# Adversarial security review — F9 `009-ask-question`

> Pre-build hard-gate review of the ask-question mutation lane spec, attacking the design on paper before any code is written. Scope: `spec.md`, `implementation-phases.md`, phase children 002/003/004, and the `research/` synthesis, checked against the existing shipped ticket/redaction/authority patterns.

## Verdict

**Not yet safe to build as written — five blocking gaps must be closed or explicitly accepted first.** The spec gets the hard things directionally right: authority stays on the host/extension, the answer is a one-use, revision-, device-, digest-, and scope-bound ticketed mutation modelled on the shipped `change-model` lane, push is content-free, and persistence is metadata-only. But the spec asserts these properties without mandating the exact mechanisms the shipped `change-model` lane uses to *enforce* them. Concretely: (1) the display-safe presentation cannot ride the "existing sync path" the spec names without being persisted or having its prompt clobbered by the canonical redactor; (2) one-use ticketing alone does not stop a question being answered twice via two distinct valid tickets — the model it copies prevents that with a single-flight lane the spec omits; (3) there is no fresh pre-handoff re-read to reject a stale answer on a concurrent supersession; (4) the digest-comparison basis is ambiguous enough to permit a spec-conforming answer-swap; and (5) the state machine routes an unconfirmed post-handoff delivery into the retryable path, which double-answers. Each is a paper defect that a careful-but-literal implementer could ship. All findings are evidence-cited; "confirmed" = read directly in the referenced file, "inferred" = reasoned from the contract.

## MUST-FIX (blocking, before build)

### MF1 — The ephemeral display payload collides with the persist-and-redact sync path: the prompt is either persisted or destroyed

**Attack / scenario.** The presented event carries `display.prompt`, option `label`/`description`, and `freeText.placeholder` (`spec.md` §Authority and protocol contract, lines 103-151). Phase 1 says these are "delivered through the existing authenticated sync channel" and "redacted before broadcast" (`spec.md`:483; `implementation-phases.md`:27; `002-.../spec.md` acceptance). But the existing sync channel has exactly one delivery primitive:

- `SyncHub.publish(candidate)` → `store.appendEnvelope(candidate)` → **broadcasts only the committed envelope** (`apps/pi-remote-relay/src/replay/sync.ts`:32-39, confirmed).
- `appendEnvelope` **persists** the envelope and, before persisting, runs `redactEnvelope` (`apps/pi-remote-relay/src/store/relay-store.ts`:188, confirmed).
- `redactEnvelope` → `redactValue` rewrites any object key that normalizes to `prompt` into `[REDACTED_PRIVATE_TEXT]` (`apps/pi-remote-relay/src/store/redaction.ts`:46, 138-141, confirmed; `PRIVATE_TEXT_KEYS = new Set(['prompt'])`).

So delivering the presentation through the named sync path forces one of two failures: the prompt and option labels are **persisted** (violating the metadata-only guarantee in `spec.md`:77-85 and AC#22/#23), or `display.prompt` is **clobbered to `[REDACTED_PRIVATE_TEXT]`** before it reaches the browser, breaking the feature. There is no existing primitive to broadcast a non-persisted envelope.

**Why the spec allows it.** The spec treats "redacted display presentation" and "metadata-only persisted block" as if one channel can carry both. The code proves they are mutually exclusive on the sync path.

**Fix.** Specify two clearly separated representations and delivery paths: (a) the metadata-only `AskQuestionTranscriptMeta` is the only thing that flows through `appendEnvelope`/sync and is persisted; (b) the display payload is produced by a **dedicated strict allowlist projector** (the pattern already used for `projectRuntimeModelCatalog`, `redaction.ts`:252-286 — allowlist, never generic key-scan) and delivered on a **non-persisted, authenticated, on-demand read** keyed by `questionId`+`revision` (mirroring `artifact:read`), never through `redactEnvelope`. State that no ask-question display content is ever passed to `redactEnvelope`/`appendEnvelope`, and that the projector is the single redaction authority for that content and is as strict as the generic policy. Do not name field `prompt` on any object that could reach `redactEnvelope`.

### MF2 — One-use ticketing does not stop a double-answer: no single-flight lane / settled-state transition

**Attack / scenario.** A client (or a compromised/misbehaving one) requests **two** valid answer tickets for question `Q` at revision `R`: `ticket1` bound to digest A, `ticket2` bound to digest B. It submits both concurrently. Each commit independently: recomputes its digest ✓, consumes its own one-use ticket ✓, sees `expectedRevision == currentRevision (R)` ✓, sees the question still "pending" ✓ (the first commit's extension handoff is async and has not settled), and hands its answer to the extension. **Two different answers are delivered to Pi for one question.** One-use is per-ticket; it does not bound the number of tickets.

**Why the spec allows it.** `spec.md`:252 and AC#16 (`spec.md`:425) require only "one `clientMutationId`, one ticket consumption, one extension callback" — that dedups identical resubmits, not two distinct tickets/`clientMutationId`s. The change-model lane this feature claims to mirror prevents the analogous race **only** through a single-flight mutation lane plus a settled-idempotency check taken *inside* the lane: `RuntimeService.enqueueMutation` serializes every mutation (`apps/pi-remote-relay/src/runtime/runtime-service.ts`:431-465, confirmed) and the revision/settled checks run inside it (:436-443, :477-486). The ask-question spec mandates no serialization and no "pending → settling" transition that a second commit would observe.

**Fix.** Require the answer commit to run in a **per-question single-flight lane** (mirroring `enqueueMutation`). The first commit must **atomically transition the question out of `pending`** before any await, so every concurrent or later commit observes `question-already-answered` and is rejected **before** handoff. Require the ticket consume itself to be atomic — synchronous validate-and-mark-consumed with no `await` in between — exactly as `consumeRuntimeModelTicket` does (`auth-service.ts`:588-611, confirmed: the ticket is deleted before the binding is even compared, so a mismatched attempt still burns it).

### MF3 — No fresh authoritative re-read before extension handoff: a stale answer can reach the extension on a concurrent supersession

**Attack / scenario.** The card is rendered at revision `R`. Between the in-memory `expectedRevision == this.revision` check and the extension handoff, a host lifecycle event supersedes or withdraws the question and advances the revision to `R+1`. An in-flight commit that already passed the in-memory compare proceeds to hand a now-stale answer to the extension.

**Why the spec allows it.** AC#19 (`spec.md`:428) requires supersede/withdraw/expiry to be rejected "before any host/extension effect," but the only stated mechanism is an in-memory revision compare against `this.revision`. The model to mirror closes this exact window with a **fresh host re-read immediately before the privileged handoff**: `refreshExecutionPrecondition` re-reads `get_state`, re-derives the revision, and returns `stale` if anything moved, *inside* the serialized lane and right before plan execution (`runtime-service.ts`:572, 595-635, confirmed). The ask-question spec has no equivalent re-verification step.

**Fix.** Require the host, inside the serialized commit lane (MF2) and immediately before handoff, to **re-verify from authoritative state** that the question is still pending at exactly the ticket-bound revision, and to fail closed (`revision-mismatch` / `question-withdrawn`) otherwise. Independently require the extension adapter to re-validate the answer against Pi's *current* pending question and reject if superseded — the extension is the final boundary and must not trust a relay-forwarded answer as still-current.

### MF4 — Ambiguous digest-comparison basis permits a spec-conforming answer-swap

**Attack / scenario.** `AskQuestionAnswerRequest` transmits both `answer` and a client-computed `answerDigest` (`spec.md`:199-208). If an implementer compares the **transmitted `answerDigest`** against the ticket-bound digest — both client-controlled — and does not recompute from the actual `answer` bytes, an attacker sends `answerDigest = A` (matching the ticket) with a different `answer` payload and the swap passes. The spec says only "The host recomputes the digest from the received answer and rejects any mismatch" (`spec.md`:211) — "mismatch against what" is unstated.

**Secondary issue — canonicalization of the answer.** `canonicalizeJson` sorts object keys but **does not sort array elements** and does not Unicode-normalize strings (`packages/pi-rpc-protocol/src/approval.ts`:22-37, confirmed). So for `selectionMode: "multiple"`, `optionIds: ["a","b"]` and `["b","a"]` produce different digests — the same logical answer has multiple digests, and a ticket bound to one order rejects the other. Unlike `canonicalizeApprovalAction`, which binds `sessionId`/`epoch`/`principal`/`policyVersion` into the hashed bytes (`approval.ts`:40-49), the ask-question digest covers only `{optionIds, freeText}`; question/revision/principal binding lives solely on ticket metadata.

**Fix.** State unambiguously that the host computes `recompute = sha256(canonicalizeJson(receivedAnswer))` and accepts **only if `recompute === ticket.boundDigest`**; the transmitted `answerDigest` is never the comparison basis (accept it only as a redundant equality check). Define a **canonical `optionIds` ordering** (e.g., sort before hashing) so a multi-select answer has one stable digest. Strongly consider binding `questionId` + `expectedRevision` + `principal` into the hashed payload (mirroring `canonicalizeApprovalAction`) as defence-in-depth so the digested bytes are self-describing rather than relying entirely on ticket-side bindings.

### MF5 — `delivery-unknown` is conflated with a retryable error, so a lost post-handoff ack double-answers

**Attack / scenario.** A commit reaches the extension/host handoff, the answer is delivered to Pi, but the acknowledgement is lost (transport drop / timeout). The result surfaces as `host-unavailable`. The state machine maps `submitting → error` for "retryable transport failure" and allows `error → submitting` "with a fresh valid ticket" (`spec.md`:350-366). Re-minting a fresh ticket and resubmitting **delivers the answer to Pi a second time**.

**Why the spec allows it.** The `AskQuestionAnswerResult.reason` enum (`spec.md`:238-248) has no distinct terminal `delivery-unknown`; it collapses all host-side loss into `host-unavailable`, and the state machine treats `error` as retryable. `spec.md`:252 says the right thing in prose ("must not resend a consumed ticket or infer acceptance from a timeout … reconciled through the existing idempotency or mutation-status mechanism"), but the typed result and the state machine contradict it. The model to mirror encodes an **explicit terminal `delivery-unknown` status that is never retried** (`runtime-service.ts`:539-547 and 702-710, confirmed).

**Fix.** Split the outcome space: a **clean pre-handoff rejection** (bad ticket, stale revision, validation failure — no host effect) is safe to retry with a fresh ticket; a **post-handoff delivery-unknown** is terminal and reconcile-only (idempotency/mutation-status lookup by `clientMutationId`), never auto-retried and never re-minted. Add a distinct `delivery-unknown` reason and forbid the state machine from routing it into `error → submitting`.

## SHOULD-FIX (strongly recommended)

- **SF1 — Validate pending-state at ticket-issue, not only at commit.** Mint the answer ticket only after a fresh re-read confirms the question is currently pending at the requested revision, mirroring `validateFreshModelTicketRequest` (`runtime-service.ts`:260-299). Otherwise authority is minted for an already-withdrawn/superseded question (wasteful; minor DoS surface). `spec.md`:93/48 requires binding but not a fresh mint-time check.

- **SF2 — Enumerate DTO guard bounds explicitly.** The new guards must use exact-key `hasOnlyKeys` allowlists and cap: `options` array length, `optionIds` array length (with uniqueness, like `isAttachmentSetManifest`'s `clientIds.size === items.length`, `guards.ts`:621-628), `freeText` byte length, and `prompt`/`label`/`description`/`placeholder` lengths; validate `answerDigest` with `DIGEST_PATTERN = /^[a-f0-9]{64}$/` (`guards.ts`:155) and reject unknown `reason`/`selectionMode`/`status` ordinals. `spec.md`:155/471 says "oversized fields" and "duplicate option IDs" but the phase tasks do not enumerate the caps, and unbounded arrays/strings are a parse-time DoS.

- **SF3 — Define selection-count semantics.** `selectionMode: "single" | "multiple"` (`spec.md`:128) does not define min/max selected options, nor whether an empty answer (no options + no free text) is valid. Specify the exact host-enforced rule (e.g., single ⇒ exactly 1; multiple ⇒ host-supplied min/max; empty allowed only when the host supplies an explicit "skip" option), so `spec.md`:224 "selection mode … is violated" has an unambiguous meaning.

- **SF4 — Require rate-limiting AND the foreground-device gate on both answer routes.** The runtime routes require a foreground device and a per-device limiter (`server.ts`:849-857 for `/api/runtime/ticket`; :926-934 for `/api/runtime/control`, confirmed). The answer-ticket and answer routes must do the same so a background/stale device cannot mint or submit answers and cannot flood. `spec.md`:478 mentions rate limiting once but not the foreground requirement, and the phase task omits both.

- **SF5 — Make metadata-only persistence structurally fail-closed via an exact-key guard.** `appendEnvelope` throws when a `transcript.block` fails `isTranscriptBlock` after redaction (`relay-store.ts`:189-195, confirmed). If the new `ask-question` transcript guard uses `hasOnlyKeys` (rejecting `display`/`answer`/`ticket`/`digest`), any projector regression that leaves display content on the block will throw at the storage boundary rather than leak. Require this as a structural property, not merely a test (AC#22).

- **SF6 — Confirm the real Pi ask-question callback contract before trusting "accepted only after Pi confirms."** The repo's extension API surface only exposes `on('tool_call', …)` (`extensions/pi-remote-approval/src/index.ts`:22-30, confirmed); the actual ask-question event/answer-callback names and their confirmation/rejection/error semantics are explicitly unknown (`spec.md`:71; `research/research.md`:27). The entire accepted-state guarantee rests on an unverified adapter. Require confirming: does the callback return an ack, throw on rejection, and how does it report "already answered"? Map those to `accepted` / `rejected` / `delivery-unknown` (MF5) before build.

- **SF7 — Bound the ephemeral display store release precisely.** `spec.md`:460 releases answer/display content on terminal states "unless the live render requires a bounded value temporarily" — too loose. Define the exact release trigger and maximum retention so prompt/answer text cannot linger in memory after `answered-immutable` / terminal.

- **SF8 — Reconcile the `answerCapability.policyVersion` type.** Typed `number` in `spec.md`:140 but `string` in `research/research.md`:67. Pick one and have the guard reject the other. Minor, but a guard written to the wrong type is a silent accept-all.

## Observations / confirmations (things the spec gets right)

- **OC1 — Authority separation is correct and strongly stated.** The relay authenticates, authorizes, routes, and redacts but must not answer; the host owns pending question, revision, lifecycle, validation, and callback (`spec.md`:441-449). This matches the shipped model where the relay never mints tool authority and the extension is the final fail-closed boundary (`index.ts`:62-96, confirmed — the handler blocks on any authorizer failure). "Tailscale/private transport ≠ mutation authority" is explicit (`spec.md`:441).

- **OC2 — Content-free push is already structurally guaranteed and reused.** `PushHintPayload` is `hasOnlyKeys(['lookupId','attentionClass'])` (`guards.ts`:304-311) and `serializePushHint` emits only those two fields (`push-service.ts`:357-363, confirmed). A pending question maps to the `needs_input` attention class; no field can carry prompt/options/answer/ticket/digest. Reuse this path unchanged (AC#23, spec.md:462).

- **OC3 — The one-use fail-closed ticket with dual revision binding is a proven pattern to mirror.** `consumeRuntimeModelTicket` deletes the ticket before comparing the binding, so even a mismatched attempt burns it (`auth-service.ts`:588-611, confirmed). Two revision checks already coexist — ticket-bound revision (:606-609) plus live revision (`runtime-service.ts`:479-486) — and the spec correctly requires both (`spec.md`:220-221). Consumption before host effect is the right order (`implementation-phases.md`:45).

- **OC4 — The digest helpers are safe to reuse.** `canonicalizeJson` sorts object keys, rejects non-finite numbers, normalizes `-0`, and drops `undefined` (`approval.ts`:22-37); SHA-256 is dependency-free (`approval.ts`:57). Two different answers cannot collide; the only caveats are array-order and Unicode normalization, which are fail-closed *mismatches* (see MF4), not collisions. The spec's instruction to reuse these and not invent a digest format is correct (`spec.md`:211).

- **OC5 — Metadata-only persistence is structurally enforceable.** `appendEnvelope` throws on a malformed transcript projection after redaction and drops control-plane residue (`relay-store.ts`:189-195, 204-206, confirmed). With a strict `ask-question` guard (SF5), display leaks fail closed.

- **OC6 — Plan-mode / `--full-access` exclusion is explicit and default-deny.** Out-of-scope and AC#25 forbid enabling plan mode or `--full-access` from the phone (`spec.md`:291, 434, 466). `authorizeAction` is a default-deny allowlist (`apps/pi-remote-relay/src/auth/policy.ts`:96, confirmed) and `MutationPolicy` is default-deny with one family at a time (`mutation-policy.ts`:19, confirmed), so an unknown/omitted answer action is denied by construction. Confirm the new `ask-question.answer` action is added to the allowlist as phone-grantable but **not** host-authoritative (`policy.ts`:85-93), and note the scope string uses a dot (`ask-question.answer`) while existing actions are colon-delimited — keep the registered action id and the scope value consistent.
