# Research charter — openclaude-android (target: specs/context/openclaude-android-main)

**Target (READ-ONLY):** specs/context/openclaude-android-main — A community fork of the leaked Claude Code / "Claw Code" coding-agent CLI (published as @gitlawb/openclaude), packaged to run on Android by extracting an embedded Linux userland (Termux/proot) and running the CLI inside it. It is a full agentic coding REPL — query engine, ~19 permission-gated tools, MCP client, multi-agent swarms, provider-agnostic — and, crucially, it ships BOTH the agent host AND a remote-control layer that lets a phone/web client drive a running local session over a WebSocket relay.

**Goal:** mine adoptable patterns for the Pi Remote SvelteKit mobile chat / remote-agent PWA. Findings only (no code changes here, no writes to the target repo). Cite file:line.

**Non-goals:** on-device inference / native modules / anything platform-specific that does not transfer to a web PWA. Never modify specs/context/**.

**Stop conditions:** convergence (newInfoRatio < 0.05) or 10 iterations.

**Angles:**
- [logic] How does the client keep a long-lived agent session alive and consistent across drops, compaction, and token expiry over a WebSocket relay?
  - extract: The close-code taxonomy (4003 unauthorized = permanent stop, 4001 session-not-found = transient-during-compaction with a 3-retry budget, others = bounded exponential backoff), 30s ping keepalive, the FlushGate that queues live writes until the history-flush POST lands so the server receives [history..., live...] in order, the BoundedUUIDSet echo-dedup ring buffer (POSTed messages come back on the read stream), the JWT refresh scheduler that rebuilds the whole transport (epoch bump) 5min before expiry, and 401-recovery that serializes against proactive refresh via an authRecoveryInFlight latch.
  - where: src/remote/SessionsWebSocket.ts, src/remote/RemoteSessionManager.ts, src/bridge/remoteBridgeCore.ts, src/bridge/flushGate.ts, src/bridge/jwtUtils.ts, src/bridge/replBridgeTransport.ts
- [architecture] What is the exact tool-permission / approval control protocol between the remote client and the agent, including plan/permission modes and rule-based 'always allow'?
  - extract: The can_use_tool control_request → allow{updatedInput} / deny{message} / ask flow; permission_suggestions carried as PermissionUpdate (addRules/replaceRules/setMode/addDirectories with userSettings/project/local/session destinations) that power 'always allow' and directory scoping; server-initiated control requests (initialize, set_model, set_permission_mode, set_max_thinking_tokens, interrupt) and the requirement to answer EVERY request (including unknown subtypes with an error) so the server doesn't hang and kill the socket after ~10-14s; the 5-value permission-mode set (default, acceptEdits, plan, bypassPermissions, dontAsk) and how set_permission_mode returns an ok/error verdict.
  - where: src/remote/RemoteSessionManager.ts, src/server/directConnectManager.ts, src/bridge/bridgeMessaging.ts (handleServerControlRequest), src/bridge/bridgePermissionCallbacks.ts, src/types/permissions.ts, src/entrypoints/sdk/controlSchemas.ts
- [other] What is the security model for authenticating and authorizing a remote client to control a coding agent, and for restricting a viewer from mutating the session?
  - extract: The ELEVATED security tier for bridge sessions and the X-Trusted-Device-Token enrollment (POST /auth/trusted_devices only within 10min of login, 90-day rolling token in OS keychain, env-var override, cache-clear on account switch); the per-instance worker-JWT closure deliberately kept OUT of process.env so it never leaks to user-configured MCP servers; the outboundOnly gate that rejects all mutable control requests with an explicit error (initialize still succeeds) and the viewerOnly flag that disables interrupts/title updates/reconnect timeout; treating web-composer-supplied filenames as untrusted.
  - where: src/bridge/trustedDevice.ts, src/bridge/workSecret.ts, src/bridge/jwtUtils.ts, src/bridge/remoteBridgeCore.ts, src/bridge/bridgeMessaging.ts, src/remote/RemoteSessionManager.ts (viewerOnly)
- [ux] How are attachments uploaded from a remote/mobile composer resolved on the agent side and injected into the prompt safely?
  - extract: The file_uuid model (web composer uploads via cookie-authed endpoint, sends {file_uuid,file_name} alongside the message; host fetches via oauth-authed GET, writes to a per-session uploads dir, injects @"path" refs); filename sanitization (basename + charset filter, uuid-prefix to avoid collisions); injecting the ref into the LAST text block (not block[0]) so [text,image] content isn't silently dropped; quoted @refs to survive home dirs with spaces; per-attachment best-effort failure that still delivers the message without the ref.
  - where: src/bridge/inboundAttachments.ts, src/bridge/inboundMessages.ts
- [ux] How does the app help a returning/backgrounded user catch up on what the agent did while they were away, and how are attention-worthy events surfaced?
  - extract: useAwaySummary's mechanism: subscribe to focus/blur state, after 5min of blur append an LLM-generated 'while you were away' summary, gated so it fires only when no turn is in progress and no summary exists since the last user turn (idempotence per turn); the focus-state 'unknown' no-op guard; the family of status/notification hooks (rate-limit, MCP connectivity, permission-needed) as a catalog of what a remote user should be pinged about.
  - where: src/hooks/useAwaySummary.ts, src/services/awaySummary.ts, src/hooks/notifs/*, src/hooks/useCancelRequest.ts
- [ease-of-use] What is the lowest-friction handshake for pairing a phone client to a running local agent session, and how is live session activity surfaced during pairing?
  - extract: The connect-URL generation and QR rendering (space-to-show/hide), the SessionActivity indicator and idle-vs-active footer text, deep-link URLs into the mobile app, and the direct-connect session creation path (server URL + wsUrl + optional bearer token) as the minimal config a client needs to attach.
  - where: src/bridge/bridgeUI.ts, src/components/BridgeDialog.tsx, src/commands/bridge/bridge.tsx, src/commands/mobile/mobile.tsx, src/server/createDirectConnectSession.ts
- [architecture] How are raw streaming agent/SDK events normalized into a render-ready transcript model, and how does the client stay forward-compatible when the backend adds new event types?
  - extract: The convertSDKMessage adapter mapping assistant / stream_event / result / system(init|status|compact_boundary) / tool_progress into internal Message/StreamEvent, plus the deliberate display decisions (suppress success results as noise, detect tool-results by content shape rather than the unreliable parent_tool_use_id, gracefully log-and-ignore unknown message types and unknown control subtypes so a newer server doesn't break an older client); the isSessionsMessage acceptance rule that avoids a hardcoded allowlist.
  - where: src/remote/sdkMessageAdapter.ts, src/remote/SessionsWebSocket.ts (isSessionsMessage), src/types/message.ts, src/utils/messages/mappers.ts
