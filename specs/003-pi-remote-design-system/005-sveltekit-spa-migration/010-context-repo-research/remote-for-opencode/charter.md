# Research charter — remote-for-opencode (target: specs/context/remote-for-opencode-master)

**Target (READ-ONLY):** specs/context/remote-for-opencode-master — A native iPhone app plus a Mac menu-bar companion that lets you start, steer, approve, and review OpenCode coding-agent sessions from your phone with zero network configuration. It solves the exact problem Pi Remote solves — remote-controlling an AI coding agent from a phone — including streaming turns, plan mode, risk-scaled command approvals, per-file diff review, attachments, backgrounding-and-resume, and push-to-approve.

**Goal:** mine adoptable patterns for the Pi Remote SvelteKit mobile chat / remote-agent PWA. Findings only (no code changes here, no writes to the target repo). Cite file:line.

**Non-goals:** on-device inference / native modules / anything platform-specific that does not transfer to a web PWA. Never modify specs/context/**.

**Stop conditions:** convergence (newInfoRatio < 0.05) or 10 iterations.

**Angles:**
- [logic] How does the turn lifecycle survive a mid-answer socket death and resume exactly where it left off, and how does on-screen vs backgrounded change the reconnection response?
  - extract: The full state machine: client-minted turn IDs; every event counted into a cursor (with 'ready'/connection events explicitly NOT advancing it); resume(from: cursor) replays-then-streams and replayed events are indistinguishable from live; the 'interrupted' event (no trailing 'done') vs 'failed' (terminal) distinction; the `active` flag deciding reconnect-now vs wait-to-be-resumed; upsert-by-stable-part-id dedupe; 'unknown' → honest reset. Note how the same controller backs both phone and desktop so the design isn't forked.
  - where: app/Shared/TurnController.swift (consume/resume/upsert), packages/RemoteKit/Sources/RemoteKit/Client/CompanionLink.swift (interrupt vs fail, Stage.streaming), docs/protocol-v1.md ("resume / transcript", "Streaming"), app/Phone/SessionView.swift (scenePhase→active, resume-on-foreground)
- [architecture] Why does the client speak a stable typed protocol v1 instead of tunneling the agent's raw HTTP/SSE, and how does the adapter + capability handshake absorb upstream churn?
  - extract: The decision to define v1 request kinds decoupled from OpenCode's API shape; `hello`→capabilities negotiation ({supportsDiff, supportsPermissions, supportsQuestions,...}) with UI degrading gracefully; the adapter subscribing to BOTH old and new event names and detecting version once; deliberately DROPPING the command `template` so the phone never parses/substitutes and can't break on upstream template changes; the two-source diff model (live-while-running vs durable-per-turn) and why each is used where; the messageID→role map needed so user messages don't render twice.
  - where: docs/protocol-v1.md (whole file — v1 kinds→OpenCode calls, "Version skew already observed"), PLAN.md ("Mobile protocol v1", adapter seam), docs/coverage.md, packages/RemoteKit/Sources/RemoteKit/Protocol/Models.swift + Wire.swift
- [ux] How are command approvals scaled by risk, turned from a bare 'no' into steering, and gated so a phone on a table can't grant anything?
  - extract: The PermissionRisk classifier (substring/prefix matching on dangerous vs harmless commands; edit paths climbing out of project → high; read/glob/grep → low) living in the shared testable core BECAUSE it's policy; three actions Allow-once/Allow-always/Reject with Reject opening a steering field; 'always' stating its scope in the button and confirming in a second step; Allow/Reject separated spatially; the biometric gate placed in front of granting only, never declining, with the no-passcode fallthrough; risk varying the card chrome.
  - where: packages/RemoteKit/Sources/RemoteKit/Protocol/PermissionRisk.swift, app/Shared/Approver.swift, app/Shared/TurnController.swift (answer(_:reply:message:)), app/Phone/ApprovalsView.swift, docs/design-spec.md §3.3, tools/uiharness/Harness/HarnessApp.swift (the rm-rf/npm-publish high-risk fixture)
- [ux] How does the app communicate 'the agent is working' — naming the activity, escalating copy over time — and how are streamed tokens throttled so live typing stays cheap?
  - extract: activity derived from the newest part that has an opinion, with plain-English verbs per tool (read→'Reading files', bash→'Running a command'); escalation ladder (0-10s activity → still going → taking a while → Stop is available) and why (~4s static = 'stuck'); show-nothing-under-1s rule; heartbeat (asymmetric pulse) not spinner; the streaming truth that message.part.updated is SNAPSHOTS while tokens are in message.part.delta, so the client accumulates per partID, throttles to ~10/sec (measured 50% fewer bytes), and flushes on idle so the last tokens aren't dropped.
  - where: app/Shared/WorkingIndicator.swift (label(after:), activityLabel extension), app/Shared/TurnController.swift (var activity), docs/design-spec.md §3.2, docs/protocol-v1.md ("Streaming: the tokens are in message.part.delta")
- [ux] How is the transcript structured without divider lines, how are the two voices separated without chat bubbles, and how does the reasoning block move through live→settled→expanded?
  - extract: The spacing-ladder-replaces-dividers rule (betweenTurns ÷ paragraph ≥ 2.0; turn starts at user message AND at agent's first part after it); user = inset tinted container, assistant = full-bleed no-container (asymmetry, no bubbles, to preserve tool framing); code blocks scroll horizontally and never wrap, no line numbers; tool activity collapses ~10 lines; the ReasoningBlock 3-state model — live height-capped auto-scrolling window, self-collapse to 'Thought for Ns' on settle, tap-to-expand — plus the bottom-anchor auto-scroll trick and top-fade mask; markdown heading compression.
  - where: app/Shared/Transcript.swift (row/startsTurn logic, ChangeSummary, PartRow), app/Shared/ReasoningBlock.swift, docs/design-spec.md §1.4 + §3.1
- [logic] How does the composer handle slash commands and attachments — one shared parser, a palette that stays above the keyboard, and image shaping enforced before send?
  - extract: SlashInput as ONE parsing function shared by the palette and the send path (the classic drift is two parsers); command() only resolves when the name is in the real known list, so typos and paths fall through to prose instead of an opaque 500; query() opens the palette while typing the name, closes once a space starts arguments; palette rendered on TOP of the composer (not a modal, keeps the keyboard) with an honest empty state; attachment pipeline: downscale to a capped long side + re-encode JPEG (vision models see a resized copy anyway), 20MB/turn enforced on BOTH ends before upload, non-images ride as-is; keep-typed-text-during-dictation ordering.
  - where: packages/RemoteKit/Sources/RemoteKit/Protocol/SlashInput.swift, app/Shared/CommandPalette.swift, app/Phone/Composer.swift, app/Shared/PromptAttachments.swift (+ RemoteKit ImageShaping.swift), app/Phone/SessionView.swift (paletteMatches, send())
- [other] How is 'policy vs plumbing' split so the risk classifier, slash parser, and diff model are unit-testable without a device, and how does the UI harness render the REAL views against canned content?
  - extract: The rule that pure decision logic lives in the shared package with real unit tests (PolicyTests, WireTests, DiffModelTests) while I/O stays out; the harness compiling the ACTUAL source views (not reimplemented copies) against mock stores selected by a launch arg, doubling as the App Store screenshot generator; coverage.md's method of auditing the agent API surface 'by weight not count' against the real OpenAPI spec to decide what's worth building — a reusable way to scope which agent capabilities a mobile client should surface.
  - where: packages/RemoteKit/Tests/RemoteKitTests/ (PolicyTests, SlashInput/Wire/DiffModel tests), docs/development.md ("Anything that is policy rather than plumbing belongs in the package"), tools/uiharness/Harness/HarnessApp.swift, docs/coverage.md
- [ease-of-use] How does 'the agent needs you' reach a backgrounded phone, get answered from the notification itself, and recover state on wake without trusting the push payload?
  - extract: Push carries only a record ID, never content → on tap the phone fetches `pending` over the authenticated channel (a poll fallback that survives missed events, no event replay needed); lock-screen Allow/Reject actions gated by device-unlock (authenticationRequired) so a table-phone can't grant; if the answer-in-place fetch fails, drop the user into the app rather than let them believe they answered; honest empty states ('Nothing is waiting on you' / 'The agent finished'); defer the notification-permission ask until pairing exists; always-present controls (model menu shows even before its catalogue loads, so a failed fetch doesn't look like a missing feature).
  - where: app/Phone/PushManager.swift, app/Phone/ApprovalsView.swift, docs/protocol-v1.md ("pending", "Push (M3, no relay)"), app/Phone/Composer.swift (ModelMenu always present), app/Shared/CommandPalette.swift (empty state)
