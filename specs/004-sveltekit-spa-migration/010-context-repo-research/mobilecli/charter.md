# Research charter — mobilecli (target: specs/context/mobilecli-main)

**Target (READ-ONLY):** specs/context/mobilecli-main — MobileCLI's Rust daemon — the desktop server half of a phone app that remote-controls AI coding CLIs (Claude Code, Codex, Gemini, OpenCode) and plain shells. It allocates a PTY per session, streams terminal bytes over a LAN/Tailscale WebSocket to a paired phone, detects when the CLI is waiting for a tool approval / plan review / question and fires a push notification, and (Pro) exposes a security-jailed filesystem browse/edit/search/upload bridge. It is the exact product category as Pi Remote, minus the client UI.

**Goal:** mine adoptable patterns for the Pi Remote SvelteKit mobile chat / remote-agent PWA. Findings only (no code changes here, no writes to the target repo). Cite file:line.

**Non-goals:** on-device inference / native modules / anything platform-specific that does not transfer to a web PWA. Never modify specs/context/**.

**Stop conditions:** convergence (newInfoRatio < 0.05) or 10 iterations.

**Angles:**
- [architecture] How does Attach-v2 achieve gap-free, dedup-safe reconnection: the deterministic clear -> chunked snapshot replay -> AttachReady -> live handoff, and how do seq/attach_id/last_live_seq/last_seen_seq cooperate to order and dedupe frames across a dropped-and-restored socket?
  - extract: The AttachBegin/AttachClear/AttachSnapshotChunk/AttachReady/PtyChunk state sequence; the 'clear canvas before replay' rule; chunked snapshot to avoid a multi-MB burst; the fresh-vs-reconnect mode flag; how live frames buffered during replay are gated then flushed; the 8MB bounded scrollback ring as the replay source.
  - where: cli/src/protocol.rs:255-400 (ServerMessage Attach* + PtyChunk + Subscribe.last_seen_seq); cli/src/daemon.rs:2369-2680 (subscribe/attach handler) and 1396-1552 (live_seq assignment); scrollback fields at daemon.rs:285-298
- [logic] How is a raw output stream classified into a normalized wait-state, and how are duplicate notifications suppressed and stale waits cleared? What is the taxonomy and the debounce/clear logic?
  - extract: WaitType enum (tool_approval | plan_approval | clarifying_question | awaiting_response) and ApprovalModel (Numbered | YesNo | Arrow | None) per CLI; the tail-focus heuristic (last 6 lines / 1200 chars) to avoid stale matches; prompt_hash dedup; the CliTracker scored identity with hysteresis + confidence buckets; the should_notify (is_new by hash/type) and should_clear (>=10 non-prompt chars) transitions.
  - where: cli/src/detection.rs (whole file — WaitType, ApprovalModel, CliTracker, detect_wait_event); cli/src/daemon.rs:1459-1520 (should_notify / clear-on-output); WaitingForInput/WaitingCleared in protocol.rs:374-386
- [other] How does the no-account pairing + challenge-response auth work, and how are per-credential capability scopes and credential revocation/rotation modeled?
  - extract: verifier = SHA256(domain||token) stored server-side only; AuthStart/AuthChallenge/AuthResponse nonce+transcript flow; proof = HMAC(verifier, transcript) with subtle::ct_eq; the scope constants (session:read/control/spawn, fs:read/write/delete/watch/upload, push:register) and has_scope gating; AuthCredential lifecycle (revoke, last_used_at) and pair --rotate / credentials revoke.
  - where: cli/src/auth.rs (whole file); ClientMessage::AuthStart/AuthResponse + ServerMessage::AuthChallenge in protocol.rs:50-68,259-264; README 'Privacy and security' + credentials/pair CLI
- [ease-of-use] What is the end-to-end onboarding/pairing UX: QR contents, connection-mode auto-detection (LAN vs Tailscale vs custom URL), and how a phone goes from scan to authenticated in one step?
  - extract: ConnectionInfo.to_compact_qr format (mobilecli://host:port?device_id&server_id&credential_id&auth_token&wss); the one-time token shown once, only verifier persisted; setup wizard mode selection with Tailscale detection (check_tailscale/get_local_ip) and custom-URL fallback; multi-device pairing (one phone -> many machines via GetSessions).
  - where: cli/src/protocol.rs:628-717 (ConnectionInfo + to_compact_qr); cli/src/setup.rs (ConnectionMode, check_tailscale, get_local_ip, prompt flow); cli/src/qr.rs; README 'Pair your phone' + docs/ARCHITECTURE_QUICK_REFERENCE.md 'Connection Flow'
- [ux] What mobile-specific UX affordances are encoded in the protocol/daemon — soft-keyboard-aware resize, chunked history to smooth perceived load, and the approval response vocabulary?
  - extract: PtyResizeReason semantic enum (AttachInit/GeometryChange/ReconnectSync/DetachRestore/KeyboardOverlay) with #[serde(other)] Unknown forward-compat; ToolApproval response set (yes | yes_always | no) mapped to approval models; desktop-safe resize policy (mobile resize doesn't force desktop window) and the touch-keyboard toolbar semantics (Esc/arrows/paste/attach); chunked snapshot as perceived-performance UX.
  - where: cli/src/protocol.rs:7-45 (PtyResizeReason, TmuxViewportAction), :134-138 (ToolApproval), :94-103 (PtyResize); README 'Real-time terminal' (touch keyboard + desktop-safe resize)
- [logic] What is the structured request/response error contract for the filesystem/attachment surface, and how are validation, rate limiting, and destructive-op opt-in expressed to the client?
  - extract: The FileSystemError enum as a client-consumed taxonomy; request_id correlation on every FS message; token-bucket RateLimiter returning retry_after_ms; path-jail + no-symlink-escape + denied/read-only glob patterns + destructive-ops-disabled-by-default; chunked FileChunk (checksum, is_last) and base64 UploadFile for attachments.
  - where: cli/src/protocol.rs:155-253 (FS ClientMessages incl UploadFile), :401-469 (FS ServerMessages incl FileChunk), :586-626 (FileSystemError); cli/src/filesystem/security.rs (PathValidator); cli/src/filesystem/rate_limit.rs
- [architecture] What is the push-notification event model — which events notify, what the payload carries, how tokens are registered/retained, and how notification work is decoupled from the stream?
  - extract: The notify trigger set and dedup coupling to prompt_hash; minimal payload (title/body/session_id only, not terminal data); RegisterPushToken/UnregisterPushToken (token_type expo|apns|fcm) and retain_active_push_tokens pruning; tokio::spawn so notification I/O never blocks streaming; build_notification_text per cli_type.
  - where: cli/src/daemon.rs:1483-1498 (async notify on should_notify), build_notification_text / send_push_notifications / retain_active_push_tokens; PushToken struct daemon.rs:137-148; RegisterPushToken/UnregisterPushToken in protocol.rs:124-133; README 'Push notifications'
