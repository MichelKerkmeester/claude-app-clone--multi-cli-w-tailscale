# Research charter — nodeterm (target: specs/context/nodeterm-main)

**Target (READ-ONLY):** specs/context/nodeterm-main — nodeterm is an Electron "node-based terminal + agent manager": real terminals and AI coding agents (Claude Code / Codex / Gemini / Grok / opencode / Copilot) live as draggable nodes on an infinite pan/zoom canvas, each in a persistent tmux session, with a kanban board of live sessions. Critically for us, the same core also runs headless as a Server Edition (browser client over WebSocket) and pairs with an iOS companion that attaches to the same live agent sessions over an end-to-end-encrypted relay — so it is the desktop/server/mobile trio of exactly the remote-agent-control problem Pi Remote solves.

**Goal:** mine adoptable patterns for the Pi Remote SvelteKit mobile chat / remote-agent PWA. Findings only (no code changes here, no writes to the target repo). Cite file:line.

**Non-goals:** on-device inference / native modules / anything platform-specific that does not transfer to a web PWA. Never modify specs/context/**.

**Stop conditions:** convergence (newInfoRatio < 0.05) or 10 iterations.

**Angles:**
- [architecture] How does nodeterm make one app codebase drive an agent core over three different carriers (Electron preload, direct browser WebSocket, E2EE relay tunnel) without the feature code knowing which?
  - extract: The RpcClient <-> FrameTransport contract: the four-method transport interface (send/onMessage/onClose/ready), how a JSON frame vs a binary frame is discriminated, how in-flight requests are failed on carrier close, how buildRelayApi/ws-bridge rebuild the SAME api surface over either carrier, and the request/cast/event/id-correlation RPC envelope shape.
  - where: src/renderer/bridge/frame-transport.ts, src/renderer/bridge/ws-bridge.ts, src/renderer/bridge/relay-api.ts, src/renderer/bridge/stubs.ts, src/shared/rpc.ts, src/shared/ipc.ts
- [other] What is the exact security envelope of nodeterm's relay, and which specific attacks does each piece defeat, given the relay itself is untrusted and forwards opaque bytes?
  - extract: The layered defenses and WHY each exists: NaCl box (Curve25519+XSalsa20-Poly1305) with per-SESSION HKDF traffic key derived from fresh nonces (defeats a relay replaying a whole recorded session because static keys give identical ECDH every reconnect); sealed-plaintext header [role][seq][tag]; strictly-increasing inbound anti-replay seq (recvSeq init -1, drop <=); role-byte-must-equal-peer check; handshake frames processed exactly once; out-of-band 6-digit SAS with mutual (both-humans-confirm) approval and pin-once peer keys; and the rule that approval may ONLY advance from a frame that came out of the E2EE box, never a plaintext relay-injected one. Note the endianness discipline traps.
  - where: src/main/remote/e2ee.ts, src/main/remote/framing.ts, src/main/remote/relay-socket.ts, src/main/remote/relay-trust.ts, src/main/remote/mutual-approval-core.ts, src/main/remote/relay-client.ts, docs/ios-protocol-migration.md (sections 2, 3, 7), docs/remote-sessions.md
- [logic] How does nodeterm reduce raw agent hook events into a reliable working/waiting/blocked/done status without race-condition false flips?
  - extract: The reduceEntry state machine and its guards: DONE_HOLDOFF (a late parallel PostToolUse 'working' arriving after Stop must not resurrect the turn), the stale-working sweeper (WORKING_STALE_MS), interrupt inference (Esc/Ctrl-C done skips the completion alert), the awaitingInput hold (Codex request_user_input keeps 'waiting' through the turn-end 'done'), the idle-rescue signal that may only move a still-'working' node, newTurn gating for per-turn fan-out reset, and which fields are transient vs persisted (and why persisting stateAt/lastEventAt would be wrong on relaunch).
  - where: src/renderer/state/agentStatus.ts, src/core/agent-status-mirror.ts, src/shared/agents/normalize.ts (NormalizedAgentEvent field docs), src/shared/agents/stale.ts
- [logic] How does nodeterm turn heterogeneous agent transcript/hook formats into one universal event shape, and how does it tail live transcripts (including subagent fan-out and context-window fill) for a remote reader?
  - extract: The NormalizedAgentEvent universal interface and the per-agent normalizers (normalizeClaude and the codex/gemini/grok variants) — what each provider's raw format looks like (see src/core/__fixtures__) and how it maps; the transcript index/reader; subagent-tail (turning Task tool-uses into live subagent cards with duration/tokens/toolUses); context-tail (deriving contextPercent); and the activity-string derivation (Edit->'Editing foo.ts', Bash->'Running <cmd>', Task->'Delegating: ...').
  - where: src/shared/agents/normalize.ts, src/core/__fixtures__/{codex,gemini,grok}, src/core/transcript-index-core.ts, src/core/transcript-reader.ts, src/core/subagent-tail.ts, src/core/context-tail.ts, docs/mobile-usage-inbox.md (activity rules)
- [ease-of-use] How does nodeterm implement Approve/Deny so it is deterministic and does not depend on injecting keystrokes into a fragile on-screen prompt — and how does a remote/mobile answerer deliver the decision?
  - extract: The hook-reply-approvals contract: the permission hook holds the request open and polls a per-decision answer file (allow|deny) that any answerer writes atomically; pendingId generation and the path-traversal validation (PENDING_ID_RE) that stops a forged id escaping the pending dir; stale-request sweeping; fail-open timeout back to the interactive prompt; and the askKind distinction (a 'question'/AskUserQuestion picker strips its pendingId so approve/deny buttons don't appear where they'd be wrong UX, vs a genuine 'approval'). Also the re-read-before-send guard: verify the node is still blocked before acting.
  - where: src/core/agents/pending-approvals.ts, docs/hook-reply-approvals.md, src/shared/agents/normalize.ts (askKind/pendingId docs), src/shared/agents/approval-mode.ts + permission-mode, src/renderer/state/permissionMode.ts
- [ux] What does the mobile companion actually show for a set of remote agents, and what is the full data contract behind that screen?
  - extract: The MirrorFile/MirrorInbox contract: InboxEvent (kind approval|question|done, title<=120, detail<=240, resolved flag) and InboxNodeNow (activity<=80, tool, contextPercent); event production rules (blocked->approval, waiting->question, done->done), title/dedup rules, resolve-on-leaving-blocked and archive-on-removal; the feed layout (unresolved on top, resolved/done under a collapsible Archived); the live-card rule (a working node with an activity string renders even with no event); and the quick-approve UX with its re-read-before-send safety.
  - where: docs/mobile-usage-inbox.md, src/core/agent-status-mirror.ts (MirrorEntry/InboxEvent/InboxNodeNow, onInboxActionable), src/main/remote-ssh/remote-status-push.ts
- [ux] How does nodeterm keep a remote session usable across drops — offline indication, reconnect-in-place, and never a dead-but-silent connection?
  - extract: The session status model (connected|connecting|offline) and takeSessionOffline that greys a tab but keeps it bound so it can reconnect IN PLACE; the relay-tab ready()-can-hang trap and its fix (race ready() against the real close signal + a timeout backstop so a dead tab always errors, never awaits forever); carrier-close handling that fails in-flight requests and shows a reconnect overlay; the WS heartbeat/reap policy (ping every 30s, one-missed-round terminate, sized to survive proxy idle timeouts); and backpressure/frame-size caps (8 MiB) as a DoS guard.
  - where: src/renderer/session/session.ts, src/renderer/session/relay-tab.ts, src/renderer/bridge/frame-transport.ts (onClose/ready), src/server/ws.ts (WS_HEARTBEAT_MS + frame cap), src/server/backpressure.test.ts
- [ease-of-use] How does nodeterm decide when to actually push a notification to the phone, so the user is pinged when it matters but not spammed or pinged while they're already watching?
  - extract: The push-notify model fed by the SAME onInboxActionable seam as the inbox: batch window (coalesce events landing close together, <=10/POST), per-node throttle (a chatty node can't spam), the presence-aware hold queue (suppress pushes while the user is present at the desktop, release when idle/locked), the grant model (push-grants / remote-push-grants — a phone drops a grant, zero open ports), and the deliberate three-surface degrade (only a standing relay host feeds it). Pair with delivery-queue's deliver-on-idle + flush-time re-validation for send-to-a-busy-or-reconnecting agent.
  - where: src/core/push-notify.ts, src/core/push-grants.ts, src/core/remote-push-grants.ts, src/core/agents/delivery-queue.ts, src/core/presence/hub.ts, src/shared/presence.ts
