## Findings

### F-01 — One actionable-event seam feeds BOTH the inbox and the push service
`createPushNotify` subscribes to `onInboxActionable` in `agent-status-mirror.ts` — the SAME seam that produces the mobile Inbox feed — so pushes fire exactly on approval/question (post-dedup) and done (turn edge), and can never disagree with what the inbox shows [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:4-8]. Payloads are a subset of `InboxEvent` (kind approval|question|done, title, nodeId, optional nodeTitle clipped to 80 chars, AskUserQuestion options/multiSelect for questions) [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:46-67]. Timestamps carry a declared unit contract: `TS_UNIT = 'unix-ms'`, forwarded verbatim from the mirror, and "nothing in this file may scale a ts" — a second producer writing seconds would make every newer-than comparison nonsense by 1000× [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:69-78].
**PWA adoption:** feed Pi Remote's web-push from the same actionable-event seam that powers its inbox screen, declare the timestamp unit once at the producer, and never re-stamp downstream.

### F-02 — Batch window coalesces close-together events; hard cap of 10 events per POST; the gate is re-checked at flush time
Constants: `DEFAULT_BATCH_WINDOW_MS = 2000`, `DEFAULT_THROTTLE_MS = 5000`, `MAX_EVENTS_PER_CALL = 10` (backend contract `events[≤10]`) [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:19-25]. A single timer schedules the flush; `flush()` splices at most 10 events and re-schedules immediately if more accumulated [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:282-289, 355-365]. Because identity/grants/settings can change during the window, the target is re-resolved at flush and the buffer is dropped if the service went inert [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:356-362]. Network errors are swallowed — there is NO retry queue in v1; the phone still polls the mirror, so a lost POST degrades to poll latency, not data loss [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:150-154, 242-247].
**PWA adoption:** coalesce web-push payloads in a ~2 s window server-side, cap arrays per request, re-validate enablement at send time, and treat the PWA's foreground poll as the retry leg instead of building a push retry queue.

### F-03 — Per-node 5-second throttle, charged only when an event is accepted
Gate order in `onEvent`: inert-check first (don't buffer), then per-kind sub-gate ("Needs you" = approval+question, "Completed" = done; both default on, master switch wins), THEN the throttle — so "a declined kind never blocks a later accepted one on the same node," and `lastPushAt` is recorded at accept time only [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:300-310, 291-298]. The 5 s/node value deliberately mirrors the desktop local-notification throttle: a chatty node cannot spam pushes [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:21-23]. When both sub-gates are off the service sends nothing while the master toggle stays honest [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:291-294].
**PWA adoption:** throttle per node/conversation, and order gates cheap→specific→throttle so a muted category never consumes another category's rate budget.

### F-04 — Presence-aware hold queue: hold alerts while the user is at the desktop, flush the still-unresolved ones on the present→away edge
While `isUserPresent()` is true at send time, accepted alerts go to a bounded in-memory HOLD queue (`HELD_QUEUE_MAX = 50`, oldest-dropped, restart loses it — documented acceptable because the mirror still carries the events) instead of POSTing [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:30-33, 330-337]. The flush trigger is an injected present→away edge (production: powerMonitor idle poll + lock-screen detection in the desktop shell); on flush, each held event is re-checked against the mirror via `isEventUnresolved` and dropped if it got resolved while waiting (an approval/question since answered, a `done` already read) [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:214-222, 342-353]. Deferral is alerts-only — the ambient live-update stream is never deferred [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:207-213]. Absent/always-false dep (Server Edition headless) reproduces exact legacy immediate-send behavior [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:209-212].
Adjacent pattern from the presence files (honestly scoped: team-presence, not the push signal): per-(client,channel) token buckets sized to the app's own honest behavior, with EDGE/clearing casts exempt from the bucket because a bucket may only drop self-correcting signals, and rate-limiting placed at the cast/request entry point where an untrusted message becomes state [SOURCE: specs/context/nodeterm-main/src/core/presence/hub.ts:30-61, 64-93, 168-199]; reflected wire strings capped by code points because they fan out down the same sink as pty output [SOURCE: specs/context/nodeterm-main/src/shared/presence.ts:97-102, 129-151].
**PWA adoption:** suppress pushes while the user has the app/workspace focused; on idle/visibility-loss edge, flush only events still unresolved; bound the hold queue and accept its ephemerality because the authoritative feed outlives it.

### F-05 — Grant model: SSH possession IS the authorization — a capability file the phone drops, zero open ports, self-healing dead-mark
A host the phone reaches by plain SSH has no relay identity, so it can push nothing via host-identity auth. Fix: the phone (which can already write on the host as the user) drops a signed, device-scoped grant token at `~/.nodeterm/push-grants/<deviceId>.grant`; a host holding that grant may push to THAT one phone only (`Authorization: Bearer <grant>`); "compromise of the host adds no new power beyond spamming its own operator" [SOURCE: specs/context/nodeterm-main/src/core/push-grants.ts:1-13]. The directory scan is tolerant at every step — missing dir, unreadable file, non-JSON, wrong schema version, missing grant string are skipped silently, so a half-written file simply does not exist until complete [SOURCE: specs/context/nodeterm-main/src/core/push-grants.ts:56-105]. The production accessor caches with a 5-min TTL plus a cheap dir-mtime gate, marks a grant dead on 401/403, and clears the dead mark when the backing file changes or vanishes — a phone that re-mints and re-drops recovers automatically; any fs error yields "no grants," never a throw [SOURCE: specs/context/nodeterm-main/src/core/push-grants.ts:145-207]. Grants are read-only artifacts, never consumed [SOURCE: specs/context/nodeterm-main/src/core/remote-push-grants.ts:32-33].
**PWA adoption:** for a self-hosted Pi backend, replace inbound-tunnel/port-forward pairing with a capability file the paired client drops over its existing access channel; fail open to "no grants" (never crash), and let re-minting heal revocations without a control channel.

### F-06 — Remote grant sweep + per-device dedupe; targeting is a UNION, and the residual double-push is documented as the cheap side of the tradeoff
Topology gap: phone --SSH--> Linux host <--SSH-- macOS nodeterm (which owns the mirror). The grant lands on the host; the pusher scans only its own $HOME — without the sweep an SSH-only user gets no push and NO ERROR (`resolveTarget` just returns null) [SOURCE: specs/context/nodeterm-main/src/core/remote-push-grants.ts:1-17]. The sweep is ONE literal `sh` line with nothing interpolated (host/project data never spliced into shell), tolerant parsing, 4096-char per-file bound where truncation yields invalid JSON and thus the tolerant skip [SOURCE: specs/context/nodeterm-main/src/core/remote-push-grants.ts:21-39, 44-72]. The cache dedupes to ONE grant per deviceId at READ time, after the dead filter, so a 401 on the first host's stale token promotes the other host's token on the very next send — self-healing with no extra round-trip; dead marks for vanished tokens are forgotten so the set cannot grow forever [SOURCE: specs/context/nodeterm-main/src/core/remote-push-grants.ts:85-118]. On the desktop, merged local+remote lists dedupe by deviceId first-wins (local first), with the same promote-on-death behavior [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:88-107]. The shared targeting rule is a UNION, not either/or: host mode fans out over the backend's `relay_devices` rows, and an SSH-only phone has no row there — its grant is its only route — so the old "paired phone excludes grants" optimization silenced every other phone on the machine with no error anywhere. The correct exclusion is per DEVICE, but the desktop cannot express it (grants keyed by deviceId; the relay registry stores only NaCl public keys; the identifiers never meet on the desktop), so a phone that is BOTH relay-paired AND granted receives TWO pushes for one event — stated plainly as the accepted cost: "a duplicate notification is a cheap regression; a phone that never rings is not." Closing it is a protocol change (backend dedupe, or persisting deviceId beside the pinned pubkey at pair time) [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:109-148].
**PWA adoption:** when multiple delivery routes exist per device, union them and dedupe per DEVICE at read time; prefer a rare duplicate over any silent never-rings failure, and write the residual imprecision down where the next maintainer will find it.

### F-07 — Deliberate three-surface degrade: the service ships everywhere but only the surface with prerequisites constructs it
`push-notify.ts` lives in `src/core` with zero electron imports, fully injected deps, pure and unit-testable, so both shells CAN boot it — but in practice only the DESKTOP shell has a standing relay-host identity + paired-phone registry; the Server Edition has neither and never constructs the service, a "documented, deliberate three-surfaces degrade" [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:10-13]. Dev builds additionally never hit the prod API (DNT + packaged gates) unless a local base is explicitly targeted [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:263-269]. The delivery queue follows the same doctrine: pure core ships on both shells, wired by one [SOURCE: specs/context/nodeterm-main/src/core/agents/delivery-queue.ts:47-53].
**PWA adoption:** build push as a pure, injectable module that degrades explicitly per deployment surface (browser PWA without a service-worker push backend = documented inert, not accidental silence), and gate dev against prod endpoints.

### F-08 — Delivery-queue deliver-on-idle: flush-time re-validation is the load-bearing property, and no outcome is ever silent
Agent-to-agent messaging refuses busy/not-idle targets, and hibernation leaves idle panes on a shell that would be refused FOREVER on exactly the nodes orchestrations most want to message; "retry in a moment" pushed onto an LLM behind a rate limiter is a token-burning busy-loop — so a `targetBusy`/hibernated target with queueing on is ENQUEUED and delivered when the target next goes idle [SOURCE: specs/context/nodeterm-main/src/core/agents/delivery-queue.ts:5-22]. Safety rests on a measurement: all four agent CLIs keep bracketed-paste (DECSET 2004) ON at idle AND during startup, so `paste-buffer -p` frames every flush including one into a still-starting agent; the one unsafe surface (a non-agent pane) is excluded by gating on NODE TYPE — the queue only enqueues what gate 1 already judged an agent pane, and the flush re-runs the WHOLE delivery so a pane that became a terminal while queued is refused, never sprayed with unframed lines [SOURCE: specs/context/nodeterm-main/src/core/agents/delivery-queue.ts:23-34]. The flush caches nothing: it calls `deliver(req)` again — the same end-to-end scope→ownership→grant→flow chain — so a grant revoked while queued comes back `notPermitted` at flush and the message is DROPPED, never delivered (pinned by a test that flips the injected deliver between enqueue and flush) [SOURCE: specs/context/nodeterm-main/src/core/agents/delivery-queue.ts:36-45]. Bounds: TTL 5 min, capacity 16 per target, and overflow REFUSES loudly (`queueFull`) rather than dropping-oldest, because "an accepted message is never silently discarded" [SOURCE: specs/context/nodeterm-main/src/core/agents/delivery-queue.ts:56-63, 173-177]. Re-queue outcomes are DERIVED from the upstream RETRYABLE set minus the queue's own outcomes, so a new retryable outcome upstream is handled the moment it exists; `rateLimited` waits for the next idle rather than re-flushing on a timer, so the queue never spins against the limiter that refused it [SOURCE: specs/context/nodeterm-main/src/core/agents/delivery-queue.ts:122-134]. Drain takes the entry off before delivering (re-entrancy safe), stops the moment the target is not ready again, re-queues at the FRONT with TTL counting from the ORIGINAL enqueue, and expiry traces AND notifies the sender — both legs — because "a silent drop is the one outcome a security core may never have"; `queued` is explicitly NOT `delivered` [SOURCE: specs/context/nodeterm-main/src/core/agents/delivery-queue.ts:19-21, 202-265].
**PWA adoption:** for send-to-a-busy-or-reconnecting-agent flows, enqueue with per-target bounds and a TTL, re-run the entire authorization chain at flush (never cache the yes), derive retry handling from the outcome vocabulary, and make expiry visible to the sender on a durable leg.

### F-09 — The live-update stream: state edges post fast, activity ticks coalesce, and a parked tick can never contradict an end edge
A second, chattier stream feeds iOS Live Activities: state edges (start / needsYou / end) post within a short 1000 ms window; activity/context ticks coalesce to ≥20 s per node; ≤20 updates per call [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:410-432]. Every edge is flagged `edge:true` so the backend can prioritize it (APNs priority 10 vs 5 for ticks — priority-5 delays were leaving the island up minutes after an answer) [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:469-473, 611-614]. Two producers fire ticks at exactly the wrong moment (raw Stop hook clearing activity; the context tail's final usage record), so a tick parked for up to 20 s would assert "working" AFTER the end went out — therefore `lastStateSent` records each edge and ticks are dropped entirely once the node is no longer working [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:534-548, 587-593, 674-681]. Done edges carry WHY: `interrupted` ("you stopped it") vs `stale` ("we lost the host" — the sweep presumed it gone), both omitted off done edges and both under a never-celebrate contract, because the mirror's message string ('Stopped') is identical for all three and a wording change must not silently alter behavior [SOURCE: specs/context/nodeterm-main/src/core/push-notify.ts:456-468, 599-604].
**PWA adoption:** split user-visible state edges from ambient progress ticks with different priorities/coalescing; suppress stale ticks once a terminal state shipped; annotate completions with cause flags instead of making clients parse prose.
