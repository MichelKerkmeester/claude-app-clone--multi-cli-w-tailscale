# Angle 6 — Session lifecycle: resume / handoff / navigation (nodeterm)

**Focus.** How nodeterm opens/focuses a session, transitions session→terminal, resumes/reconnects after a
drop, hands off between devices/hosts, pairs remotely (QR/tweetnacl), and reconciles stale state — mapped
onto OUR host-authoritative, fail-closed session→chat navigation and `id`+`epoch` re-validation.

**Constraint tags:** (a) client-side view affordance over existing DTO fields · (b) pure interaction/layout
pattern · (c) needs a new host read-only field/RPC.
**Verdicts:** ✅ drop-in · ⚠️ needs a host field/RPC · ❌ not portable (extract the pattern only).

**What nodeterm is (why most of its *mechanism* is ❌).** nodeterm SPAWNS and OWNS local PTYs, runs tmux, does
SSH, and writes files on remote hosts. That ownership is ❌ for us — our client owns no session truth and
re-validates `id`+`epoch`, failing closed. The prize here is the *decision logic and state discipline* around
reconnect, resume-marking, and navigation precedence, which is strikingly aligned with fail-closed.

**Orca dedup baseline (Angle 6 + host-requests already cover):** carry the opaque id RAW + re-validate
`id`+`epoch` at chat entry (6.1); navigation-intent precedence, selected vs host-active vs navigation-requested
(6.2); live-edge FAB vs per-turn arrow (6.3); load-earlier pagination (6.4); per-session device-local view-mode,
fail-closed if the pref store is unreadable (6.5); authorized file-link routing (6.6). Host-requests Open-Q#1 is
answered: the Inbox `AttentionItemDto` keys on `lookupId`, carries **no** `sessionId`. Findings below say where
nodeterm REINFORCES or ADDS to these — none of them re-promote an orca win unchanged.

## Summary read

nodeterm's session-lifecycle code is unusually aligned with our fail-closed stance because its own reconnect
path faces the same hazard (a lost hook event stranding a `working` node) and answers it the same way: default
to *undecided*, never locally promote uncertainty to a terminal state, and let the authoritative side (the
host) re-assert truth. The highest-leverage ports are all **pure interaction/logic (category b, ✅)** — none
require a new host field to ship, though two connect to the existing host-request set as guardrails.

**Host-dependent (c) items:** none are new requests. ND-6.1's server-side resync and ND-6.6's staleness-as-`unknown`
are already satisfied by our relay re-pushing a fresh snapshot + `noteRelayHeartbeat` on reconnect; they'd only
become a host request (`serverTime`/heartbeat field) if we ever consumed a host-pushed *status blob* directly,
which we don't.

**Standouts:** ND-6.1 (default-undecided + live-vs-idle asymmetry — the correct fail-closed default, not merely
cautious) and ND-6.2 (close-vs-drop → reconnect-in-place, never vanish the chat view or duplicate it) are the two
HIGH wins. ND-6.3 (race any pending open against close+timeout, never hang) and ND-6.7 (fail-closed QR/enrollment
pairing) harden the *connection-establishment* boundary that orca's Angle 6 didn't touch.
