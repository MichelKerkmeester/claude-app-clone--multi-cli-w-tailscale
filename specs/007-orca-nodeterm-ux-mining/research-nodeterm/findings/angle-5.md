# Angle 5 — Composer / input (esp. dictation) — nodeterm

Target: `specs/context/nodeterm-main` (read-only). Maps onto OUR composer:
`app-mobile/src/pages/chat/chrome/session-composer.svelte` + `composer-tools.svelte` +
`composer-command-autocomplete.svelte` + `attachments/`.

## Framing (read before the table)

**nodeterm has NO chat composer.** Its "input" is the terminal itself (xterm + tmux) running an
agent CLI, so the classic composer surfaces the brief lists — prompt-history recall, `@`-mentions,
slash-suggestion, send-gating — are all owned by the *CLI inside the pane*, not by nodeterm, and are
**not portable** (they don't exist to copy). The one genuinely portable, fully-implemented composer
feature nodeterm owns is **dictation** (`src/core/speech/` + `src/renderer/.../DictationOverlay.tsx`),
and it is a real on-device Whisper pipeline, not chrome. This angle therefore weights heavily to
dictation (ND-5.1–5.5) and treats the rest as thin reinforcements/negatives.

**Constraint check for dictation under host-authoritative + fail-closed:** on-device STT is
**client-side interaction (b)** and constraint-safe *because the transcript is inserted as an
editable draft the user still confirms before send* — byte-identical to typing. It only becomes
`⚠️ (c)` if audio is shipped to a host STT RPC. nodeterm proves both the safe insertion contract
and the fail-closed setup/permission states orca only sketched as "chrome" (orca 4.6). Our mobile
client has **no dictation today** (grep of `app-mobile/src`: zero `getUserMedia`/`dictat`/`speech`
hits), so this is net-new.
